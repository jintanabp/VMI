# 11 — คู่มือนักพัฒนา (สำหรับผู้รับช่วงงาน)

เอกสารฉบับนี้จัดทำขึ้นสำหรับ **ผู้พัฒนาที่เข้ามาดูแลโปรเจกต์ต่อ** เมื่ออ่านจบควรสามารถ
แก้ไขและต่อยอดระบบได้โดยไม่กระทบส่วนที่ทำงานอยู่เดิม

- ต้องการทราบว่าระบบ *ทำหน้าที่อะไร* → [01 — ภาพรวมโปรเจกต์](./01-overview.md)
- ต้องการทราบว่า *ผู้ใช้เห็นหน้าจออย่างไร* → [04 — คู่มือผู้ใช้](./04-user-guide.md)

## 1. การติดตั้งครั้งแรก

```bash
git clone <repo> && cd VMI
npm install                  # postinstall จะเรียก prisma generate ให้อัตโนมัติ
cp .env.example .env         # อ่านคำอธิบายส่วนหัวของไฟล์ ต้องกำหนดจริงประมาณ 21 บรรทัด
npm run db:setup             # สร้างฐานข้อมูล SQLite พร้อมข้อมูลตัวอย่าง
npm run dev                  # ต้องใช้ port 3000 เท่านั้น
```

เปิดที่ <http://localhost:3000/vmi/> — ต้องมี `/vmi` ต่อท้ายเสมอ

### เหตุผลที่ต้องใช้ port 3000

Redirect URI ที่ลงทะเบียนไว้กับ Azure ผูกกับ `localhost:3000` หากใช้ port อื่น
การเข้าสู่ระบบฝั่งเซลล์จะไม่ทำงาน สคริปต์ `scripts/check-dev.mjs` ตรวจสอบให้ก่อนเริ่มระบบแล้ว

### การเข้าใช้งานระหว่างพัฒนา

| ต้องการเข้าใช้ในบทบาท | วิธีดำเนินการ |
|---|---|
| เซลล์ / ผู้ดูแลระบบ | ต้องมี Azure app จริง (ดู README) และกำหนดอีเมลของตนเองใน `ADMIN_EMAILS` |
| ร้านค้า (วิธีเร็วที่สุด) | เข้าสู่ระบบเป็นผู้ดูแล แล้วเปิด `/vmi/admin/preview/vda` เพื่อเลือกรหัส VDA |
| ร้านค้า (ทดสอบขั้นตอนจริง) | กรอกอีเมลที่หน้าเข้าสู่ระบบ → อนุมัติคำขอที่ `/vmi/admin/stores/accounts` → กำหนดรหัสผ่าน (อย่างน้อย 8 ตัวอักษร) |

> **ข้อควรทราบ:** เดิมผู้ใช้สามารถเข้าเป็นร้านค้าได้โดยเลือกรหัส VDA เท่านั้น ไม่ต้องใช้รหัสผ่าน
> ตั้งแต่วันที่ 28 สิงหาคม 2569 ช่องทางดังกล่าวสงวนไว้สำหรับผู้ดูแลระบบเท่านั้น
> หากพบเอกสารที่ระบุว่าเลือกรหัส VDA แล้วเข้าใช้งานได้ทันที เอกสารนั้นล้าสมัยแล้ว

## 2. หลักการสำคัญ 6 ข้อ

ทำความเข้าใจหลักการเหล่านี้ก่อน จะช่วยให้อ่านโค้ดส่วนที่เหลือได้เร็วขึ้นมาก

### 2.1 ข้อมูลแบ่งเป็น 2 ประเภท และต้องไม่ปะปนกัน

| ประเภท | แหล่งที่มา | สิทธิ์การเขียน | จัดเก็บที่ |
|---|---|---|---|
| **Master** — สินค้า ราคา โปรโมชัน ยอดขาย ทะเบียนพนักงานขาย | Microsoft Fabric (OneLake) | **อ่านอย่างเดียว** | ไฟล์ CSV ใน `data/cache/` แล้วนำเข้าหน่วยความจำ |
| **Transaction** — คำสั่งซื้อ PO บัญชีร้าน MIN/MAX การแจ้งเตือน | ระบบนี้สร้างขึ้นเอง | เขียนได้ | SQLite ผ่าน Prisma |

หากพบโค้ดที่พยายามเขียนข้อมูลกลับไปยังฝั่ง master ถือว่าผิดหลักการ เนื่องจากข้อมูล master
จะถูกดึงมาทับใหม่ทุกคืนในรอบ sync

### 2.2 ค่าที่ใช้ประกอบการตัดสินใจต้องบันทึกไว้ ไม่คำนวณใหม่ขณะอ่าน

เมื่อร้านค้ากดส่งคำสั่งซื้อ ระบบจะบันทึกราคา C4 ส่วนลด โปรโมชัน ของแถม และค่า MIN/MAX
ลงใน `OrderItem` ทันที

เนื่องจากราคาและโปรโมชันเปลี่ยนแปลงทุกวัน หากคำนวณใหม่ขณะเปิดดูคำสั่งซื้อย้อนหลัง
ตัวเลขจะไม่ตรงกับที่ร้านค้าเห็นขณะตัดสินใจ ทำให้ไม่สามารถตรวจสอบย้อนหลังได้
และสถานะธงราคาจะเปลี่ยนไปมา

ฟิลด์ที่ขึ้นต้นด้วย `c4` ใน `OrderItem` คือข้อมูลชุดนี้ **ห้ามเปลี่ยนไปใช้การคำนวณสด**

### 2.3 ตัวตนของร้านค้าต้องมาจาก session ที่ลงลายเซ็นแล้วเท่านั้น

```ts
// ถูกต้อง — เป็นช่องทางเดียวที่อนุญาต
import { getAuthorizedStore } from "@/lib/auth/store-context";
const authorized = await getAuthorizedStore();
if (!authorized) return NextResponse.json({ error: "..." }, { status: 401 });

// ห้ามใช้ — cookie นี้เป็นค่า cuid ที่ไม่ได้ลงลายเซ็น สามารถปลอมแปลงได้
const storeId = cookieStore.get("vmi_store_id")?.value;
```

cookie `vmi_store_id` มีคุณสมบัติ httpOnly ซึ่งป้องกันการเข้าถึงจาก JavaScript ได้
แต่ไม่สามารถป้องกัน HTTP request ที่ประกอบขึ้นเองได้ เดิมทั้งระบบใช้ค่านี้เป็นตัวระบุตัวตน
ทำให้ผู้ที่กำหนด cookie เป็นรหัสของร้านอื่นสามารถเข้าถึงและแก้ไขข้อมูลของร้านนั้นได้

### 2.4 basePath คือ `/vmi` — ห้ามประกอบ URL เอง

```ts
import { appPath } from "@/lib/paths";
apiFetch(appPath("/api/stock"));   // ถูกต้อง — ได้ /vmi/api/stock
fetch("/api/stock");               // ผิด — จะได้ 404 บน production
```

ฝั่ง client ให้ใช้ `apiFetch` แทน `fetch` เนื่องจาก `apiFetch` จะส่ง `UnauthorizedError`
เมื่อได้รับสถานะ 401 และตัวจัดการส่วนกลางใน `components/providers.tsx` จะนำผู้ใช้
ไปยังหน้าเข้าสู่ระบบให้ หากใช้ `fetch` โดยตรง ผู้ใช้ที่ session หมดอายุจะพบข้อความแสดง
ข้อผิดพลาดค้างอยู่พร้อมปุ่มลองใหม่ที่ไม่มีทางสำเร็จ

### 2.5 ห้ามใช้กล่องโต้ตอบของเบราว์เซอร์

`window.confirm()` `alert()` และ `prompt()` หยุด main thread ทั้งหน้าไว้จนกว่าจะมีผู้ตอบ
และเมื่อระบบถูกเปิดผ่าน webview กล่องอาจไม่ปรากฏให้ผู้ใช้เห็นเลย อาการที่ผู้ใช้พบคือ
"กดปุ่มแล้วหน้าเว็บค้าง" ซึ่งเคยเกิดขึ้นจริงในหน้า `/manage`

ให้ใช้ `ConfirmDialog` สำหรับการยืนยัน และ `Modal` สำหรับกล่องทั่วไป ทั้งสองตัวอยู่ใน
`components/ui` และผูกกับ `hooks/use-focus-trap.ts` ให้แล้ว

หากจำเป็นต้องเขียน portal ขึ้นเองจริง ๆ (เช่น `C4PromoModal` และ `PoDetailPanel` ที่มี
โครงเฉพาะตัว) ต้องเรียก `useFocusTrap(ref, open)` ด้วยตนเอง มิฉะนั้นการกด Tab จะทำให้
โฟกัสหลุดไปยังเนื้อหาที่อยู่หลังกล่อง

### 2.6 การแจ้งเตือนต้องไม่ทำให้งานหลักล้มเหลว

`notifyStore()` และ `notifySales()` มีการดักจับข้อผิดพลาดไว้ภายในตัวเองแล้ว หากการบันทึก
การแจ้งเตือนล้มเหลว การอนุมัติคำสั่งซื้อต้องยังคงสำเร็จ **ไม่ควรนำการเรียกใช้ฟังก์ชันเหล่านี้
ไปวางในตำแหน่งที่ข้อผิดพลาดสามารถส่งต่อออกมาได้**

## 4. ข้อควรระวังที่เคยก่อให้เกิดปัญหาจริง

รายการต่อไปนี้เป็นข้อผิดพลาดที่เกิดขึ้นจริงในระบบ ไม่ใช่กรณีสมมติ

### 4.1 โปรโมชันแบบกลุ่ม — ของแถมปรากฏในทุกบรรทัด

โปรโมชันที่รวมยอดข้าม SKU จะส่งข้อมูล `freeGood` **ชุดเดียวกัน** มาพร้อมกับทุกบรรทัดในกลุ่ม
เนื่องจากของแถมเป็นสิทธิ์ของ *กลุ่ม* ไม่ใช่ของแต่ละบรรทัด

หากนำมารวมโดยตรง จำนวนของแถมจะถูกคูณตามจำนวนสมาชิกในกลุ่ม (กรณีจริงคือกลุ่ม `BSWM`
ที่ควรได้รับ 600 ชิ้น แต่การรวมโดยตรงให้ผลลัพธ์ 3,000 ชิ้น)

**ต้องรวมยอดผ่าน `collectOwedFreeGoods()` เท่านั้น** ห้ามเขียน `.reduce()` ขึ้นใหม่

### 4.2 การนำบรรทัดในกลุ่มโปรโมชันออก ทำให้ราคาบนเอกสารผิดพลาด

หากนำสมาชิกของกลุ่มออกจากใบสั่งซื้อ บรรทัดที่เหลือจะยังคงถือข้อมูล
`c4PromoGroupMembers` `c4PooledQty` และ `c4DiscountBaht` ของกลุ่มเต็มซึ่งไม่เป็นจริงแล้ว
ส่งผลให้ส่วนลดที่พิมพ์ลงเอกสารสำหรับฝ่ายจัดซื้อเป็นส่วนลดที่ร้านค้าไม่ได้รับจริง

ด้วยเหตุนี้ ฟังก์ชัน "อนุมัติเฉพาะบางรายการ" (A1b) จึงยังไม่สามารถดำเนินการได้
รายละเอียดอยู่ใน `docs/IMPROVEMENT-PLAN.md`

ปัจจุบันบรรทัดที่มีจำนวนเป็น 0 จะถูกตัดออกจากเอกสาร **เฉพาะกรณีที่ไม่ได้อยู่ในกลุ่มโปรโมชัน**
ส่วนบรรทัดที่อยู่ในกลุ่มจะคงไว้พร้อมหมายเหตุสำหรับผู้ตรวจสอบ

### 4.3 การอนุมัติต้องจองสิทธิ์ก่อนดำเนินการใด ๆ

`approveWithPoSplit` ทำงานตามลำดับต่อไปนี้ และ**ห้ามสลับลำดับ**

```
ตรวจสอบ → จองสิทธิ์ (compare-and-set) → ออกเลข PO → เขียนไฟล์ → สร้างระเบียน PO
```

เลขที่ PO ไม่สามารถนำกลับมาใช้ซ้ำได้ และไฟล์เอกสารถูกเขียนลงดิสก์จริง
หากใช้รูปแบบอ่านสถานะก่อนแล้วจึงเขียน (read-then-act) ผู้ใช้สองคนที่กดอนุมัติพร้อมกัน
จะผ่านขั้นตอนการอ่านทั้งคู่ ต่างฝ่ายต่างออกเลขที่ PO จากนั้นฝ่ายที่ล้มเหลวจะเกิดข้อผิดพลาด
ภายหลัง โดยที่เลขที่ PO ถูกใช้ไปแล้วและมีไฟล์เอกสารตกค้างในระบบ

มีชุดทดสอบครอบคลุมที่ `tests/approve-with-split.db.test.ts`

### 4.4 `decidedBy` เป็น `String @default("")` ไม่ใช่ค่าที่รับ null ได้

การเขียนค่า `null` ลงในฟิลด์นี้จะทำให้ `updateMany` เกิดข้อผิดพลาด และหากข้อผิดพลาดนั้น
เกิดขึ้นภายในบล็อก rollback **คำสั่งซื้อจะค้างอยู่ในสถานะ `approved` โดยไม่มี PO**
ซึ่งเป็นสถานะที่กลไก rollback มีไว้เพื่อป้องกันโดยตรง

### 4.5 ข้อมูลยอดขายย้อนหลังมีเพียง 30 วัน ไม่ใช่ 120 วัน

ค่า `MAX_DAYS_KEPT = 120` ใน `lib/fabric/sold-history.ts` เป็นเพดานของฝั่งระบบนี้
แต่ **ข้อมูลจากต้นทางมีเพียง 30 วัน** เนื่องจาก Fabric notebook กำหนด `LOOKBACK_DAYS = 30`
และเขียนทับไฟล์ทุกคืน

ฟังก์ชัน `getSummary` จะเติมค่า 0 ให้กับวันที่ไม่มีข้อมูล หากร้องขอช่วง 90 วันจะได้ค่าศูนย์
ที่ไม่เป็นจริงจำนวน 60 วัน และค่าเฉลี่ยจะต่ำกว่าความเป็นจริง 3 เท่า ปัญหานี้แก้ไขแล้วด้วย
`clampWindowToCoverage()` — **ให้ใช้ `summary.effectiveDays` เป็นตัวหารเสมอ
ห้ามใช้จำนวนวันที่ผู้ใช้ร้องขอ**

### 4.6 `npm run build` แจ้งว่าไม่พบโมดูลทั้งที่โค้ดถูกต้อง

สาเหตุคือ `npm run dev` ยังทำงานอยู่ ทั้งสองคำสั่งใช้โฟลเดอร์ `.next/` ร่วมกัน

```bash
npm run dev:stop && npm run build
```

**ไม่ควรเสียเวลาตรวจสอบไฟล์ที่ข้อความแสดงข้อผิดพลาดอ้างถึง** เนื่องจากไม่ใช่ข้อผิดพลาดจริง

### 4.7 การยกเลิกคำสั่งซื้อโดยร้านค้าคือการลบระเบียน

`app/api/store/orders/route.ts` ใช้คำสั่ง `prisma.order.delete()` ไม่ใช่การเปลี่ยนสถานะ
จึงไม่มีคำสั่งซื้อที่มีสถานะ `"cancelled"` อยู่ในฐานข้อมูล (เงื่อนไขที่ตรวจสอบค่านี้เป็นโค้ด
ที่คงไว้เผื่อการเปลี่ยนแปลงในอนาคต) และคำสั่งซื้อที่ร้านค้ายกเลิกจะ**ไม่ปรากฏในสถิติทุกประเภท**
รวมถึงตัวหารของอัตราการอนุมัติ

### 4.8 การอ่านไฟล์ CSV ต้องใช้ตัวอ่านของโปรเจกต์

`lib/fabric/csv.ts` รองรับเครื่องหมาย `"` ที่ปรากฏกลางค่าข้อมูล เช่น หน่วยวัดนิ้ว (`12" x 4"`)
เคยเกิดกรณีข้อมูล SKU หายไป 15 รายการจากการแยกข้อความด้วยเครื่องหมาย `,` โดยตรง
ปัจจุบันมีชุดทดสอบครอบคลุมแล้ว

### แนวทางการเขียนชุดทดสอบ

ทดสอบเฉพาะ **ตรรกะล้วน** ที่มีผลกระทบสูงเมื่อทำงานผิดพลาด โดยไม่ครอบคลุม component
และ API route เนื่องจากต้องอาศัย DOM หรือฐานข้อมูล ทำให้ชุดทดสอบทำงานช้าและเปราะบาง
ส่วนที่คุ้มค่าที่สุดคือสูตรคำนวณและกฎทางธุรกิจที่เคยเกิดข้อผิดพลาดจริง

**ข้อยกเว้นเดียว** คือไฟล์ที่ลงท้ายด้วย `.db.test.ts` ซึ่งใช้ฐานข้อมูล SQLite ชั่วคราวได้
สำหรับตรรกะระดับ `lib/` ที่เป็นทรานแซกชันจริงและไม่สามารถพิสูจน์ด้วยฟังก์ชันบริสุทธิ์ได้
เช่น การอนุมัติพร้อมกัน โดยยังคงห้ามใช้กับ API route และ component

### การเขียนชุดทดสอบที่ต้องใช้ฐานข้อมูล

```ts
import { createTestDatabase, setTestDatabaseUrl, seedPendingOrder } from "./helpers/test-db";

const db = createTestDatabase("ชื่องาน");
setTestDatabaseUrl(db.url);              // ต้องเรียกก่อน import โมดูลที่จะทดสอบ
const { approveWithPoSplit } = await import("@/lib/po/approve-with-split");
```

`lib/prisma.ts` อ่านค่า `DATABASE_URL` ขณะสร้าง client เพียงครั้งเดียว หาก import
ก่อนกำหนดค่า ชุดทดสอบจะเขียนข้อมูลลงฐานข้อมูลสำหรับพัฒนาจริง

## 6. ขั้นตอนการทำงานที่พบบ่อย

### การเพิ่ม API route

1. สร้างไฟล์ `app/api/<ชื่อ>/route.ts`
2. **ตรวจสอบสิทธิ์เป็นลำดับแรกเสมอ** โดยใช้ `getAuthorizedStore()` สำหรับฝั่งร้านค้า
   หรือ `getSalesSession()` / `getRawSalesSession()` สำหรับฝั่งเซลล์และผู้ดูแลระบบ
3. ใช้ zod ตรวจสอบข้อมูลที่รับจากผู้ใช้
4. เพิ่มรายการใน [05 — API Reference](./05-api-reference.md)

### การเพิ่มสถานะ PO

แก้ไขที่ `lib/po/po-status.ts` เพียงไฟล์เดียว เนื่องจากคอลัมน์ในฐานข้อมูลเป็นชนิด `String`
ไม่ใช่ enum จึง**ไม่ต้อง migrate** ค่าเดิมที่ไม่ตรงกับรายการใหม่จะแสดงเป็น "ไม่ทราบสถานะ"
โดยระบบยังทำงานได้ตามปกติ หากเพิ่ม tone ใหม่ต้องเพิ่มคลาสใน `PO_STATUS_CLASS` ด้วย

หากสถานะใหม่ควรแจ้งให้ร้านค้าทราบ ต้องเพิ่มการแจ้งเตือนที่
`app/api/sales/purchase-orders/[poNumber]/route.ts`

### การเพิ่มชนิดการแจ้งเตือนร้านค้า

1. `lib/orders/store-notify.ts` — เพิ่มค่าใน `StoreNotificationKind`
2. `lib/orders/store-notify-display.ts` — เพิ่มใน `NOTIF_META` **และ** `notifTone`
3. ปรับคำอธิบายใน `prisma/schema.prisma` (เป็นความคิดเห็นเท่านั้น ไม่ต้อง migrate)

### การเพิ่มตารางข้อมูลจาก Fabric

แก้ไขที่ `lib/fabric/datasets.ts` มีชุดทดสอบ (`dataset-specs.test.ts`) กำหนดว่าทุก dataset
ต้องระบุชื่อไฟล์ต้นทางของตนเองได้โดยไม่ต้องอาศัยตัวแปรสภาพแวดล้อม

### การเพิ่มตัวแปรสภาพแวดล้อม

ต้องกำหนดค่าเริ่มต้นที่ปลอดภัยไว้ในโค้ดเสมอ แล้วจึงอธิบายไว้ใน `.env.example`
**ระบบต้องไม่ทำงานผิดพลาดโดยไม่มีสัญญาณเตือนเมื่อไม่ได้กำหนดค่า** หากเป็นค่าที่ขาดไม่ได้
ให้ตรวจสอบและหยุดการทำงานตั้งแต่ขั้นตอน boot ใน `instrumentation.ts`
ตามตัวอย่างใน `lib/auth/session-secret.ts`

## 7. รายการตรวจสอบก่อนส่งมอบงาน

```bash
npm test                 # 1. ชุดทดสอบต้องผ่านทั้งก่อนและหลังการแก้ไข
npx tsc --noEmit         # 2. ต้องไม่มีข้อผิดพลาดด้านชนิดข้อมูล
npm run dev:stop         # 3. หยุด dev ก่อน build เสมอ
npm run build            # 4. build ต้องสำเร็จ
npx next lint            # 5. ต้องไม่มี warning เพิ่มขึ้นจากเดิม
```

**ข้อ 6 สำคัญที่สุด: เปิดหน้าจอจริงเพื่อตรวจสอบผลลัพธ์** การ build สำเร็จไม่ได้หมายความว่า
ระบบทำงานถูกต้อง

ขนาดหน้าจอที่ต้องทดสอบ ได้แก่ จอ desktop และ **จอความกว้างต่ำกว่า 1280px**
(iPad หรือหน้าต่างครึ่งจอ) ซึ่งเป็นจุดที่พบปัญหาบ่อย

## 8. ข้อควรทราบก่อนนำขึ้นใช้งานจริง

รายละเอียดทั้งหมดอยู่ใน [09 — Production Deploy](./09-deployment.md) สรุปจุดที่พบปัญหาบ่อย

| หัวข้อ | ข้อควรระวัง |
|---|---|
| `NEXTAUTH_SECRET` | ระบบ production จะ **ไม่เริ่มทำงาน** หากไม่ได้กำหนด สั้นกว่า 32 ตัวอักษร หรือยังเป็นค่าตัวอย่าง (ออกแบบให้หยุดทำงานทันทีเพื่อให้ตรวจพบได้เร็ว) |
| การเปลี่ยน secret | ผู้ใช้ทุกคนจะออกจากระบบพร้อมกัน ควรเปลี่ยนเมื่อมีเหตุจำเป็นเท่านั้น |
| nginx | path `/vmi/` ต้องมีเครื่องหมาย `/` ปิดท้าย เนื่องจาก `trailingSlash: true` ทำให้ path ที่ไม่มี `/` ตอบกลับด้วยสถานะ 308 |
| healthcheck | ต้องใช้ `curl -fsSL` พร้อม `/` ปิดท้าย มิฉะนั้น curl จะผ่านสถานะ 308 โดยไม่ได้เรียก handler จริง |
| backup | ต้องทำก่อน `prisma migrate deploy` เสมอ เนื่องจาก migration ที่ลบคอลัมน์ไม่สามารถย้อนกลับได้ |
| อีเมลแจ้งเตือน | ต้องกำหนด **ทั้ง** `ALERT_EMAIL` และ `SENDER_EMAIL` มิฉะนั้นระบบจะข้ามการส่งโดยไม่แจ้งเตือน |

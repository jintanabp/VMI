# ส่วนที่ 3 — เฟส 2: ส่ง PO จริง ⛔ ยังไม่เริ่ม

> **ห้ามเริ่มเขียนขาส่งก่อนได้คำตอบข้อ 4.1–4.4** — ยิง production ผิดใบเดียว
> คู่ `orderNo`+`customerCode` จะถูกล็อก **6 เดือน** = เผาเลข PO ทิ้งถาวร

### [ ] 3.1 env gate ก่อนอย่างอื่น
- `ERP_BILL_API_URL` (**default ว่าง = ทั้ง pipeline เป็น no-op** ปุ่มถูกปิดพร้อมเหตุผล) + `ERP_BILL_API_TIMEOUT` (15 วิ)
- **ต้องการ:** URL ของ **UAT** เท่านั้นในช่วงทดสอบ · เพิ่มคำอธิบายใน `.env.example` ตามกติกาโปรเจกต์
- **ขาด:** ยังไม่มี UAT (ดูข้อ 4.2)

### [ ] 3.2 ที่เก็บผลการส่ง (ต้อง migrate)
- เพิ่มบน `PurchaseOrder`: `erpSentAt` · `erpAttemptedAt` · `erpError` · `erpInsertedRows`
- VMI มี 1 แถวต่อ 1 PO และ `poNumber @unique` อยู่แล้ว **จึงไม่ต้องมีตาราง staging แยก**เหมือน ocr ที่เก็บรายบรรทัด
- **ต้องการ:** `npx prisma migrate dev` บนเครื่อง + **`npx prisma migrate deploy` บนเซิร์ฟเวอร์** ตอน deploy
  · สำรอง DB ก่อน (`npm run backup:db`)

### [ ] 3.3 `lib/po/erp-delivery.ts` — ตัวส่ง
- ลำดับ: ประกอบ → ตรวจความพร้อม → POST → **สำเร็จเมื่อ HTTP 200 *และ* `body.success === true` เท่านั้น**
  (HTTP 200 อย่างเดียวไม่พอ — ฝั่ง ocr มีเทสต์คุมข้อนี้)
- ประทับ `erpSentAt` ด้วย compare-and-set `updateMany({ where: { poNumber, erpSentAt: null } })` แล้วเช็ค `count === 1`
  (แพตเทิร์นเดียวกับ `lib/po/approve-with-split.ts`)
- **บทเรียนจาก ocr ที่ต้องลอก:** WHERE ต้องระบุให้แคบพอที่จะไม่ประทับใบอื่น — ฝั่งเขาใช้คู่
  `source_order_id` + `orderno` เพราะเลข PO ไม่ unique ข้ามเวลา · ของเราเลข unique อยู่แล้วแต่ยังต้องมี `erpSentAt: null`
- **ล้มเหลว:** เขียน `erpError` ไม่แตะ `erpSentAt` (ยังอยู่ในคิว) + แจ้งเซลส์ผ่าน `notifySales()` — **ไม่ auto-retry**

### [ ] 3.4 นโยบาย timeout — จุดที่อันตรายที่สุด
- ถ้า POST สำเร็จฝั่ง ERP แต่ response หายกลางทาง: ยิงซ้ำจะโดน duplicate = **เผาเลข PO 6 เดือน**
- สเปก **ไม่มี idempotency key** ⇒ timeout ต้องให้ **คนไปตรวจก่อน** ห้ามให้ระบบยิงซ้ำเอง

## บล็อกอยู่จริง ต้องได้ก่อนเริ่มเฟส 2

### 4.1 `deliveryDate` เอาจากไหน 🔴
VMI **ไม่มีวันนัดส่งในระบบเลย** (ต่างจากฝั่ง OCR ที่เซลส์กรอกจากใบ PO ของลูกค้า)
ตัวเลือก: วันอนุมัติ + N วัน (N เท่าไหร่) · ให้เซลส์เลือกตอนกดส่ง · หรือใช้วันอนุมัติเลย
- **กระทบ:** ทุกใบขึ้นว่า "ยังส่งไม่ได้" อยู่ตอนนี้เพราะข้อนี้ข้อเดียว
- **จุดที่ต้องแก้เมื่อได้คำตอบ:** `erpDeliveryDate()` ใน `lib/po/erp-context.ts` — **ฟังก์ชันเดียว**

### 4.2 ขอ UAT + รหัสลูกค้าทดสอบ 🔴
- **กระทบ:** ไม่มี UAT = ทดสอบขาส่งไม่ได้เลย และ production ห้ามแตะ
- ⚠️ UAT ของเขาตรวจ **หลวมกว่า** prod (ยอมรับบรรทัด `F` บนออเดอร์ปกติ และกฎ duplicate ต่างกัน) — ผ่าน UAT ไม่ได้แปลว่าผ่าน prod

### 4.3 ราคาที่ไม่ตรง C4 จะให้ทำยังไง 🔴
VMI ให้แก้ราคาได้ และแบ่ง PO ตาม `priceKind` = `c4 / override / mixed` อยู่แล้ว
ถ้าส่งเป็นออเดอร์ปกติพร้อม `unitPrice` ที่ไม่ตรง C4 — **ระบบวางบิลจะยึดตัวเลขของเรา หรือคิดใหม่จาก C4?**
- **สถานะตอนนี้:** ตัวตรวจติดธง `price_off_c4` ให้ (2 จาก 4 ใบในเครื่องนี้เข้าเงื่อนไข)
- ตรวจเรื่อง `isErrorC4` เต็ม ๆ แล้ว — **ดูส่วนที่ 4.3ก ข้างล่าง** ก่อนจะตอบข้อนี้

### 4.3ก ผลตรวจ `isErrorC4` — ทำไมยังไม่ใช้ และใช้แล้วจะเสียอะไร
ตรวจเมื่อ **11 ก.ย. 69** จากสเปก prod ของปลายทางและโค้ดที่ ocr-po-matching ใช้งานจริง
(`~/Documents/GitHub/ocr-po-matching`) ไม่ใช่การอนุมาน

**1) ตั้ง `isErrorC4` เดี่ยว ๆ ไม่ได้ — สเปกบังคับให้มาคู่กับ `isSpecial`**
`docs/ocr-insertOCROrderToBill-prod.md:27,53` ระบุตรง ๆ ว่า `isErrorC4=Y` ต้องมี `isSpecial=Y` ด้วย
ไม่งั้นตอบ 400 (`isSpecial must be 'Y' when isErrorC4 is 'Y'` — บรรทัด 217) ·
ฝั่ง ocr จึงตั้งสองตัวนี้พร้อมกันเสมอ และ **normalize ให้เองใน `build_payload`** เผื่อแถวเก่าตั้งมาตัวเดียว
(`backend/erp_export.py:307-311`) ⇒ คำถามนี้ไม่ใช่ "จะใช้ `isErrorC4` ไหม" แต่เป็น "จะยอมส่งใบนี้เป็น
special deal ไหม"

**2) พอเป็น special deal ปลายทางเลิกคิดโปรให้ — และโครงข้อมูลของเราจะทำให้ร้าน "ของแถมหาย"**
กติกาในสเปก: ออเดอร์ปกติ (`isSpecial` ว่าง) ปลายทาง **คิดโปรใหม่จาก C4 เอง** จึงห้ามส่งบรรทัด `F`;
พอตั้ง `isSpecial=Y` บรรทัด `F` กลายเป็นสิ่งที่ **เราต้องส่งเอง** (สเปกบรรทัด 51-53)
- VMI เก็บของแถมเป็น **attribute ของบรรทัดซื้อ** (`OrderItem.c4FreeGoodCode/Qty/Unit`) ไม่ใช่บรรทัดแยก
  `buildErpPayload` จึงสร้างแต่บรรทัด `B` — **ไม่มี `F` สักบรรทัดเดียว**
- ⇒ ถ้าวันนี้เปิด `isSpecial=Y` ขึ้นมาเฉย ๆ ใบนั้นจะเข้าไปเป็นดีลที่ **ของแถมเป็นศูนย์**
  ไม่ใช่ error ที่ไหนสักแห่ง แต่เงียบ ๆ แล้วร้านไม่ได้ของ
- ของที่ต้องสร้างก่อนถึงจะเปิดทางนี้ได้: แปลง `c4FreeGood*` เป็นบรรทัด `F`
  (`unitPrice`/`amount`/`vatAmount` = 0, `promotionTo` ชี้สินค้าที่ทำให้ได้แถม) โดยรวมยอดด้วย
  `collectOwedFreeGoods()` ที่ `lib/promo/order-free-goods.ts` เพราะโปรกลุ่มซ้ำอยู่ทุกบรรทัด
- **หมายเหตุ:** ฐานข้อมูลในเครื่องนี้ยังไม่มีบรรทัดไหนมีของแถมเลย (0 จาก 2,434 บรรทัด)
  ความเสี่ยงข้อนี้จึงเป็นเชิงโครงสร้าง ยังวัดจากข้อมูลจริงไม่ได้

**3) "ราคาไม่ตรง C4" ของเรา กับ `isErrorC4` ของเขา ไม่ใช่เรื่องเดียวกัน**

| | VMI (`priceFlagged`) | ocr-po-matching (`ERRC4`) |
|---|---|---|
| เทียบอะไร | **ราคาตั้งต่อหีบ** เทียบสแนปช็อต `c4UnitPrice` | **ส่วนลด/ของแถม** เทียบที่ C4 บอก |
| ค่าความคลาดเคลื่อน | `PRICE_MATCH_EPSILON` 0.005 บาท | `DISCOUNT_TOLERANCE` 0.50 บาท |
| ขั้นโปร | ระบบคิดจาก C4 เสมอ **คนตั้งเองไม่ได้** | เซลส์กรอกเองได้ จึงต้องมีตัวตรวจ |
| ที่มา | `lib/calculations/price-override.ts` | `backend/c4_alignment.py` |

ของเราคือ "โต้แย้งราคาแคตตาล็อก" ส่วนของเขาคือ "ส่วนลดที่ให้ไปไม่ตรงโปร" ⇒ **แมป
`priceKind !== "c4"` เป็น `isErrorC4` ตรง ๆ ไม่ได้** มันตอบคนละคำถาม
แต่ผลปลายทางเรื่องเงินเหมือนกัน: บิลที่ออกไม่ตรงกับที่ตกลงกับร้าน ซึ่งคือเหตุผลที่ฟิลด์นี้มีอยู่
(`c4_alignment.py:14-19` — "ไม่ว่าจะให้มากกว่าหรือน้อยกว่า C4 ก็ถือว่าไม่ตรง")

**4) เงินที่เถียงกันอยู่ วัดได้แล้วจากข้อมูลจริงในเครื่อง**
4 บรรทัดที่ติดธง ทั้งหมด `reason=mismatch` และต่างกันทั้งสองทาง:

| รหัส | หีบ | C4 | ราคาที่ใช้จริง | ต่าง/หีบ | ส่วนลด C4 บนบรรทัดนี้ |
|---|---|---|---|---|---|
| 469205 | 3 | 660 | 700 (ร้านตั้ง) | +40 | 70 บาท/หีบ |
| 208363 | 4 | 676 | 700 (ร้านตั้ง) | +24 | 180 บาท/หีบ |
| 111302 | 4 | 1,050 | 1,020 (เซลส์ตั้ง) | −30 | — |
| 111310 | 1 | 1,050 | 1,000 (ร้านตั้ง) | −50 | — |

**2 ใน 4 บรรทัดมีทั้งราคาที่แก้เองและส่วนลด C4 ทับอยู่** ซึ่งเป็นเคสที่ตัวเลขสองฝั่ง
ไม่มีทางตรงกัน: VMI คิดส่วนลดทับ**ราคาที่แก้แล้ว** (`resolveEffectivePrice` →
`calcNetUnitPrice`) เช่น 469205 ได้สุทธิ 700 − 70 = **630/หีบ** แต่ถ้าปลายทางคิดใหม่จากฐานของตัวเอง
จะได้ 660 − 70 = **590/หีบ** ⇒ ต่างกัน 40 × 3 หีบ = **120 บาท เฉพาะบรรทัดเดียว**

**5) คำถามที่ต้องถามจริง ๆ (แทนข้อ 4.3 เดิมที่กว้างเกินจะตอบ)**
- **4.3-ก** ออเดอร์ปกติ (`isSpecial` ว่าง) ระบบวางบิล **ใช้ `unitPrice`/`amount` ที่เราส่งไปไหม**
  หรือไปหยิบราคาจาก C4 มาคิดเอง? (ถ้าใช้ของเรา ใบ `override` ส่งได้เลย ไม่ต้องทำอะไรเพิ่ม)
- **4.3-ข** ถ้าคิดใหม่ — `isSpecial=Y` + `isErrorC4=Y` เป็นทางเดียวใช่ไหม
  และพอเป็น special deal แล้ว **เราต้องส่งบรรทัด `F` เองครบทุกชิ้นใช่ไหม**
- **4.3-ค** ใบที่ติด `isErrorC4=Y` ต้องมีคนอนุมัติฝั่ง ERP ก่อนออกบิลไหม (ฝั่ง ocr แบ่ง PO
  แยกตามภาคเพราะ "marketing อนุมัติใบ error เป็นภาค" — `c4_alignment.propose_split`)
  ถ้าใช่ ฝั่ง VMI ต้องรู้ว่าใครเป็นคนอนุมัติ

**เชิงอรรถเรื่อง `unitPrice` กับ `amount`** — เราส่ง `unitPrice` เป็น**ราคาก่อนลด** และ `amount`
คิดจาก**ราคาหลังลด** ซึ่งดูขัดกันเองเมื่ออ่านผ่าน ๆ แต่**ตรงกับที่ ocr ทำจริง**
(`backend/sgo_billing.py:92` — `amount = round(qty * (unitprice - per_case_off), 2)`) และตรงกับ
ตัวอย่างในสเปกที่ไม่มีส่วนลด (`unitPrice 403.74` → `amount 403.74`) ⇒ **ไม่ใช่บั๊กของเรา**
แต่ก็แปลว่าถ้าปลายทางคิด `amount` ใหม่จาก `unitPrice` ตรง ๆ ตัวเลขจะเพี้ยนทันทีโดยไม่ต้องรอเรื่อง C4
— ซึ่งคำถาม 4.3-ก ครอบคลุมอยู่แล้ว

**ระหว่างรอคำตอบ ไม่ต้องแก้โค้ดอะไร** — ตัวตรวจกันใบกลุ่มนี้ไว้แล้วด้วย `price_off_c4`
และ `deliveryDate` ก็ยังกันทุกใบอยู่ดี · ทางออกที่แพงน้อยที่สุดถ้าคำตอบคือ "ปลายทางคิดใหม่"
คือส่งเฉพาะกลุ่ม `A` (ราคาตรง C4) แล้วกันกลุ่ม `B` ไว้ — ซึ่ง **VMI แบ่งให้อยู่แล้ว**
ที่ `proposePoSplit` และ `validatePoSplit` ก็กันไม่ให้กลุ่มโปรเดียวกันถูกหั่นข้าม PO อยู่แล้ว
(กฎเดียวกับ `propose_split` ของ ocr)

### [x] 5.2 แท็บ "รหัสผ่าน" ไม่มีฟอร์มเปลี่ยนรหัส

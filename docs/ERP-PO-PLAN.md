# ส่วนที่ 3 — เฟส 2: ส่ง PO จริง ⛔ ยังไม่เริ่ม

> **ห้ามเริ่มเขียนขาส่งก่อนได้คำตอบข้อ 4.1–4.4** — ยิง production ผิดใบเดียว
> คู่ `orderNo`+`customerCode` จะถูกล็อก **6 เดือน** = เผาเลข PO ทิ้งถาวร

### [ ] 3.1 env gate ก่อนอย่างอื่น
- `ERP_BILL_API_URL` (**default ว่าง = ทั้ง pipeline เป็น no-op** ปุ่มถูกปิดพร้อมเหตุผล) + `ERP_BILL_API_TIMEOUT` (15 วิ)
- **ต้องการ:** URL ของ **UAT** เท่านั้นในช่วงทดสอบ · เพิ่มคำอธิบายใน `.env.example` ตามกติกาโปรเจกต์
- **ขาด:** ยังไม่มี UAT (ดูข้อ 4.2)

### [ ] 3.2 ที่เก็บผลการส่ง (ต้อง migrate)
- เพิ่มบน `PurchaseOrder`: `erpSentAt` · `erpAttemptedAt` · `erpError` · `erpInsertedRows`
- VMI มี 1 แถวต่อ 1 PO และ `poNumber @unique` อยู่แล้ว **จึงไม่ต้องมีตาราง staging แยก**เหมือน ocr ที่เก็บรายบรรทัด
- **ต้องการ:** `npx prisma migrate dev` บนเครื่อง + **`npx prisma migrate deploy` บนเซิร์ฟเวอร์** ตอน deploy
  · สำรอง DB ก่อน (`npm run backup:db`)

### [ ] 3.3 `lib/po/erp-delivery.ts` — ตัวส่ง
- ลำดับ: ประกอบ → ตรวจความพร้อม → POST → **สำเร็จเมื่อ HTTP 200 *และ* `body.success === true` เท่านั้น**
  (HTTP 200 อย่างเดียวไม่พอ — ฝั่ง ocr มีเทสต์คุมข้อนี้)
- ประทับ `erpSentAt` ด้วย compare-and-set `updateMany({ where: { poNumber, erpSentAt: null } })` แล้วเช็ค `count === 1`
  (แพตเทิร์นเดียวกับ `lib/po/approve-with-split.ts`)
- **บทเรียนจาก ocr ที่ต้องลอก:** WHERE ต้องระบุให้แคบพอที่จะไม่ประทับใบอื่น — ฝั่งเขาใช้คู่
  `source_order_id` + `orderno` เพราะเลข PO ไม่ unique ข้ามเวลา · ของเราเลข unique อยู่แล้วแต่ยังต้องมี `erpSentAt: null`
- **ล้มเหลว:** เขียน `erpError` ไม่แตะ `erpSentAt` (ยังอยู่ในคิว) + แจ้งเซลส์ผ่าน `notifySales()` — **ไม่ auto-retry**

### [ ] 3.4 นโยบาย timeout — จุดที่อันตรายที่สุด
- ถ้า POST สำเร็จฝั่ง ERP แต่ response หายกลางทาง: ยิงซ้ำจะโดน duplicate = **เผาเลข PO 6 เดือน**
- สเปก **ไม่มี idempotency key** ⇒ timeout ต้องให้ **คนไปตรวจก่อน** ห้ามให้ระบบยิงซ้ำเอง
- **ต้องการ:** คำตอบข้อ 4.8 (ถามได้ไหมว่าใบนั้นเข้าไปแล้วหรือยัง / resend ได้ไหม)

### [ ] 3.5 UI ปุ่มส่ง + สถานะ
- ปุ่ม "ส่งเข้า ERP" ขึ้นเฉพาะเมื่อ **พร้อม** และ **ตั้ง URL แล้ว** — ไม่พร้อมให้ปิดปุ่มพร้อมเหตุผล (มี reason label ครบแล้ว)
- เพิ่มสถานะ `sending` / `sent_erp` ใน `lib/po/po-status.ts` — **ไม่ต้อง migrate** (สถานะเก็บเป็น String โดยตั้งใจ)

### [ ] 3.6 อ่านสถานะกลับจาก ERP (ทำท้ายสุด)

# ส่วนที่ 4 — คำถามที่ต้องได้คำตอบ (ส่งได้เลย)

## บล็อกอยู่จริง ต้องได้ก่อนเริ่มเฟส 2

### 4.1 `deliveryDate` เอาจากไหน 🔴
VMI **ไม่มีวันนัดส่งในระบบเลย** (ต่างจากฝั่ง OCR ที่เซลส์กรอกจากใบ PO ของลูกค้า)
ตัวเลือก: วันอนุมัติ + N วัน (N เท่าไหร่) · ให้เซลส์เลือกตอนกดส่ง · หรือใช้วันอนุมัติเลย
- **กระทบ:** ทุกใบขึ้นว่า "ยังส่งไม่ได้" อยู่ตอนนี้เพราะข้อนี้ข้อเดียว
- **จุดที่ต้องแก้เมื่อได้คำตอบ:** `erpDeliveryDate()` ใน `lib/po/erp-context.ts` — **ฟังก์ชันเดียว**

### 4.2 ขอ UAT + รหัสลูกค้าทดสอบ 🔴
- **กระทบ:** ไม่มี UAT = ทดสอบขาส่งไม่ได้เลย และ production ห้ามแตะ
- ⚠️ UAT ของเขาตรวจ **หลวมกว่า** prod (ยอมรับบรรทัด `F` บนออเดอร์ปกติ และกฎ duplicate ต่างกัน) — ผ่าน UAT ไม่ได้แปลว่าผ่าน prod

### 4.3 ราคาที่ไม่ตรง C4 จะให้ทำยังไง 🔴
VMI ให้เซลส์แก้ราคาได้ และแบ่ง PO ตาม `priceKind` = `c4 / override / mixed` อยู่แล้ว
ถ้าส่งเป็นออเดอร์ปกติพร้อม `unitPrice`/ส่วนลดที่ไม่ตรง C4 — **ระบบวางบิลจะยึดตัวเลขของเรา หรือคิดใหม่จาก C4?**
- ถ้าคิดใหม่: ราคาที่ร้านกับเซลส์ตกลงกันไว้จะไม่ถูกใช้ · ทางที่ ERP ออกแบบมาให้คือ `isSpecial=Y` + `isErrorC4=Y`
  ซึ่ง **พี่สั่งห้ามใช้** ⇒ ต้องตัดสินใจร่วมกันว่าใบกลุ่มนี้จะส่งหรือกันไว้
- **สถานะตอนนี้:** ตัวตรวจติดธง `price_off_c4` ให้ (2 จาก 4 ใบในเครื่องนี้เข้าเงื่อนไข)

### 4.4 เน็ตออกจากเซิร์ฟเวอร์ VMI ไปถึง `spcws/spcuatws.sahapat.com` ได้ไหม 🔴
- **คนละเส้นกับ OneLake** ที่ใช้อยู่ (ของ ocr ต่อได้เพราะรันอยู่คนละเครื่อง)
- **ต้องการ:** ให้ทีม infra ยืนยัน/เปิดทาง · endpoint นี้ **ไม่มี auth เลย** เป็น public endpoint ในเครือข่าย

### 4.6 `salesmanCode` ควรส่งของใคร 🟡

### 4.7 เลข `orderNo` รูปแบบ `V1`–`V6` + `YYMMDD` + ลำดับ (+ ตัวอักษรกลุ่ม) ใช้ได้ไหม 🟡

# ส่วนที่ 5 — งานค้างอื่นที่เจอจากการทดลองใช้ (รอพี่เคาะขอบเขต)

### [ ] 5.1 มือถือ render การ์ดทั้ง 836 ใบ ไม่มี virtualization
- เดสก์ท็อปมี virtualizer (เปิดเมื่อ ≥40 แถว) แต่โหมดการ์ดบนมือถือไม่มี
- **บน headless ไม่ช้า** แต่บนมือถือจริงของร้านยังไม่รู้
- **ต้องการ:** วัดด้วย CPU throttling 4–6 เท่าใน Chrome (ผมทำได้ ~10 นาที) แล้วค่อยตัดสินว่าคุ้มทำไหม

### [ ] 5.2 แท็บ "รหัสผ่าน" ไม่มีฟอร์มเปลี่ยนรหัส
- มีแค่ปุ่ม "ขอรีเซ็ตรหัสผ่าน" (ส่งลิงก์ทางอีเมล) — คนที่ล็อกอินอยู่แล้วเปลี่ยนรหัสเองไม่ได้
- **ต้องการ:** การตัดสินใจว่าร้านควรเปลี่ยนรหัสเองได้ไหม (เป็นเรื่อง auth flow ไม่ใช่ UI)

### [ ] 5.3 ค่าที่พิมพ์ในหน้า manage หายเมื่อสลับแท็บ
- พิมพ์ MIN/MAX ค้างไว้ → ไปแท็บ "หยุดสั่ง" → กลับมา ค่ากลับเป็น 7/15 โดยไม่มีข้อความบอก
  (คำค้นและแบรนด์ที่กางไว้ยังอยู่ — ไม่สม่ำเสมอ)
- **ต้องการ:** เลือกทางระหว่าง (ก) คงคอมโพเนนต์ไว้ตอนสลับแท็บ (ข) เตือนก่อนออกจากแท็บ

### [ ] 5.4 รายการหยุดสั่งบางเกินไป
- ไม่มีค้นหา/เรียง · ไม่บอกว่าใครสั่งหยุดและเมื่อไหร่ · empty state ไม่บอกว่าไปเพิ่มที่ไหน
- ตอนนี้มีรายการเดียวจึงยังไหว — **ต้องการ:** ขอบเขตที่ต้องการเมื่อรายการเยอะขึ้น

### [ ] 5.5 ปฏิทิน 2 แบบในการ์ดเดียวกัน (หน้าหยุดสั่ง)
- มุมมองอ่านโชว์ "28 ส.ค. 69" (พ.ศ. 2 หลัก) แต่ช่องแก้เป็น `2026-08-28T13:59` (ค.ศ.)
- แก้ได้แบบเดียวกับที่ทำกับตัวกรอง PO (echo วันที่เป็นไทยข้างช่อง) — งานเล็ก

### [x] 5.6 จำนวนแนะนำปัดขึ้นเสมอ (`ceil`) — **ตัดสินใจแล้วว่าคงไว้**
**พี่เคาะเมื่อ 10 ก.ย. 69: "ไม่ปรับแล้วกัน เอาแบบเดิม"**
- ตัวเลขที่เคยเสนอ (ถ้าใช้กติกา 30% แบบเดียวกับโปร): เปลี่ยน 50 จาก 154 แถว · หีบรวม 1,885 → 1,835 ·
  มูลค่า 1,501,875 → 1,460,173 บาท · ทุกแถวที่เปลี่ยนยังอยู่เหนือ MIN
- **อย่าเสนอซ้ำ** — ปัดลงในจำนวนแนะนำ = เสี่ยงของขาด ต่างจากปัดลงในโปรที่เสียแค่ของแถม
- ⚠️ **ห้ามสับสนกับการปัดขั้นโปร** (`planPromoStepRound` — 30% / 50% เมื่อขั้นใหญ่กว่า 12 หีบ) ซึ่งทำเสร็จแล้วและเป็นคนละตัว
